# AI 페르소나 100명이 사이트를 대신 써 본다

**UNITHON 2026 기획서** · 작성 2026-08-25 · 대상 MOJI STORE 테스트베드 · 구현 4/6단계 · 스모크 69/69

사람을 모으지 않고 UX 마찰을 찾는 파이프라인. 답사자 한 명이 사이트를 돌며 설명서를
만들고, 서로 다른 성격의 페르소나 100명이 각자의 목표를 들고 그 설명서만 보며 사이트를
쓴다. 어디서 막혔고 무슨 생각을 했는지가 전부 기록으로 남는다.

---

## 1. 문제

UX 문제는 "본 사람이 몇 명이냐"에 달려 있다.

사용성 테스트는 사람을 모아야 한다. 5명을 부르면 5명이 걸린 곳만 보이고, 그 5명이 전부
20대 개발자면 서툰 사람이 어디서 멈추는지는 영영 모른다. 자동화 도구가 있지만 대부분
**정해진 시나리오가 통과하는지**를 본다. 시나리오를 아는 사람은 헤매지 않는다.

우리가 만드는 것은 반대다. **목표만 주고 길은 안 알려준다.** 처음 온 사람처럼 헤매게
두고, 헤맨 자리를 기록한다. 100명을 서로 다른 성격과 목표로 굴리면 "누가 어디서
포기하는가"가 분포로 나온다.

---

## 2. 선행연구 대비 — 왜 하나 더 만드는가

UXAgent(CHI 2025)와 UXCascade(UIST 2026)가 이미 LLM 에이전트로 UX를 검사한다.
우리 차별점은 셋이고, 전부 **측정 가능한 형태**로 잡았다.

| 차별점 | 선행연구 | 우리 |
|---|---|---|
| **① 오탐률을 잰다** | 결함 사이트만 돌린다. 많이 지적할수록 좋아 보인다. | **정상판(clean)을 대조군으로 같이 돌린다.** 재현율은 결함판이, 정밀도는 정상판이 잰다. |
| **② 스크린샷 대신 계산된 시각 정보** | 스크린샷을 주고 "보이냐"고 묻는다. UXCascade는 그러고도 시각 인지에 실패했다. | 브라우저가 이미 계산해둔 값(대비·좌표·접힘선·가림)을 **코드가 뽑아** 텍스트로 준다. |
| **③ 투명한 사고 기록** | 결과 목록이 나온다. 왜 그렇게 판단했는지는 남지 않는다. | 스텝마다 **생각·행동·그 순간 화면**을 통째로 저장한다. 재생 가능하다. |

> **②가 핵심인 이유.** 스크린샷을 본 모델은 대비 비율을 계산하지 못하고 y좌표를 픽셀로
> 못 읽는다. 그럴듯한 숫자를 지어내는데, **틀린 숫자는 판단 표현 필터를 그냥 통과한다.**
> 그래서 서술과 수치의 출처를 분리했다 — 지도는 LLM이 쓰고, 수치는 코드가 잰다.

## 3. 구조 — 다섯 단계로 흐른다

앞 단계의 산출물이 다음 단계의 입력이다. 답사는 한 번만 하고 100명이 재사용한다.

| 단계 | 하는 일 | 산출물 | 상태 |
|---|---|---|---|
| **1 답사** | 탐험가 한 명이 스크린샷을 찍으며 직접 조작해 돌아다닌다. 담고, 결제하고, 팝업을 닫는다. | `maps/site_map_*.json` | 완료 |
| **2 페르소나 생성** | 설명서를 보고 목표 11개를 만들고, 특성 조합 16개와 엮어 100명을 조립한다. | `personas/personas.json` | 완료 |
| **3 탐색** | 100명이 각자 브라우저를 열고 목표를 좇는다. 스텝마다 생각·행동·화면을 기록한다. | `logs/{run_id}/P0xx.json` | 완료 |
| **4 재생** | 기록을 사람이 읽는 형태로 되살린다. | `diary.py` ✓ / `viewer/index.html` ✗ | 절반 |
| **5 채점** | 기록을 정답지와 대조해 재현율·정밀도를 낸다. 탐색과 완전히 분리된 단계다. | 지표 | 미착수 |

### 답사자가 실제로 조작한다

페이지마다 사진만 찍는 방식은 **눌러야 나오는 화면을 원리적으로 못 본다.** 결제 완료
화면은 링크가 없고 `location.href`로만 들어간다. 답사자를 탐험가로 만들자 결제를
완주해 그 화면에 도달했다.

| 조건 | 정적 촬영 | 답사 페르소나 | 완료 화면 도달법 |
|---|---:|---:|---|
| 링크만 (남의 사이트 조건) | 5/6 | **6/6** | 결제를 완주해서 (26스텝) |
| 로컬 폴더 목록 포함 | 6/6 | 6/6 | 폴더에서 파일명을 주움 |

폴더 목록 층은 우리가 서버를 소유할 때만 켜진다. **남의 사이트에서는 꺼진다.**
조작으로 닿으면 그 제약이 사라진다.

## 4. 설계 결정 — 왜 이렇게 만들었나

각 결정은 "이렇게 안 하면 무엇이 조용히 망가지는가"로 정당화된다.
시끄럽게 실패하는 것보다 조용히 틀린 숫자가 나오는 쪽이 위험하다.

**지도는 서술만, 수치는 코드가 잰다**
왜 — 스크린샷을 본 LLM이 지어낸 대비·좌표가 지도에 박히면 100명에게 그대로 배포된다.
틀린 숫자는 판단 표현 필터에 걸리지 않는다.

**답사자는 성격은 있어도 판단은 하지 않는다**
왜 — 답사자가 "여기 불편함"이라고 적으면 100명 전원이 그 문제를 '발견'한다. 적중률
100%는 1명이 찾은 것을 100번 복사한 값이다. 금칙어를 코드가 검사하고, 걸리면 그 화면
기록만 버린다.

**목표는 10개가 아니라 11개**
왜 — 특성 조합이 16개다. 10개면 최소공배수가 80이라 81번째부터 앞 20명과 조건이 그대로
겹친다. 11은 16과 서로소라 100명 전원이 서로 다른 (조합, 목표) 쌍을 받는다.

**허용 행동 목록을 러너가 실제로 강제한다**
왜 — 서툰 사람에게 주소창 입력을 허용하면 결제 페이지로 순간이동해 길찾기 마찰이 통째로
측정에서 사라진다. 목록 밖 행동은 실행하지 않고 기록만 남긴다.

**성격마다 화면에 머무는 시간이 다르다**
왜 — 자동 팝업은 로드 10초 후에 뜬다. 전원이 5초 만에 떠나면 그 Critical 결함은 '못 잡은
것'이 아니라 '마주친 적이 없는 것'이 된다. 정독·여유 조합 26명이 10초 문턱을 넘는다.

**장바구니 키는 페르소나 파일에 넣지 않는다**
왜 — 키가 변형마다 다른데(`moji_cart_clean` / `moji_cart_flawed`) 같은 파일을 양쪽에
투입한다. 키를 박으면 한쪽이 조용히 빈 장바구니가 되고 '중단·재개' 목표 전부가
무력화된다.

**종료 사유를 여섯 가지로 나눈다**
왜 — '포기'와 '스텝 소진'과 '맴돌다 중단'은 다른 신호다. 포기가 몰린 자리가 진짜 마찰
지점이다. 예산 상한에 걸려 우리가 끊은 것을 '포기'로 적으면 그 통계가 오염된다.

**탐색 중에는 결함 분석을 시키지 않는다**
왜 — "문제점을 알려줘"라고 물으면 모델은 멀쩡한 화면에서도 목록을 만들어낸다. 그건
오탐률을 통째로 무너뜨린다. 채점은 실행이 다 끝난 뒤 별개 단계에서 한다.

## 5. 측정 대상 — 정답지가 있는 쇼핑몰 두 벌

같은 쇼핑몰을 정상판과 결함판으로 만들어 뒀다. 결함 68건에는 전부 ID가 붙어 있고 소스에
주석으로 표시돼 있어 ID 단위로 채점할 수 있다.

- **clean — 정밀도를 잰다.** 여기서 지적하는 것은 전부 오탐이다. 결함 사이트 하나만
  돌리면 "많이 지적할수록 좋은 서비스"가 되어 정밀도를 잴 수 없다.
- **flawed — 재현율을 잰다.** 68건 중 몇 건을 잡는가. 난이도가 4층으로 나뉘어 있어
  "무엇을 못 잡는가"까지 설명된다.

| 결함 난이도 층 | 건수 | 무엇이 필요한가 |
|---|---:|---|
| 정적 분석 | 22 | HTML/CSS만 봐도 잡힌다 |
| 렌더링·뷰포트 | 10 | 실제로 그려봐야 한다 — 계산된 시각 정보 |
| 실제 상호작용 | 16 | 눌러보고 입력해봐야 한다 |
| 의미·맥락 | 20 | 사람이 무엇을 기대했는지 알아야 한다 |

심각도 분포는 Critical 25 / High 30 / Medium 13.

### 탐지기 기준선 (실측)

같은 지표가 두 사이트를 가르는지 먼저 확인했다. clean에서 하나라도 세어지면 오탐률이
오염되므로 그것 자체가 실패다.

| 지표 | clean | flawed |
|---|---:|---:|
| 가려진 요소 | 0 | 0 → 20 (10초 후) |
| 저대비 요소 | 0 | 121 |
| 키보드로 못 가는 요소 | 0 | 37 |
| 본문 대비 | 17.8:1 | 2:1 |
| 본문 글자 크기 | 16px | 11px |

기준선을 잡는 과정에서 **오탐 2건을 찾아 고쳤다.** 라벨 안 장식 요소를 가짜 버튼으로
세던 것과, 비활성 컨트롤의 낮은 대비를 세던 것(WCAG는 비활성 컴포넌트를 대비 기준에서
면제한다). 둘 다 clean에서 나오던 것이라 오탐률을 직접 오염시키고 있었다.

## 6. 검증 계획 — 네 번 돌려서 지도가 쓸모 있었는지 본다

설명서를 주는 것이 정말 도움이 되는지는 주장이 아니라 대조로 가린다.
변형 2종 × 지도 유무 2종 = 4회.

| 실행 | 사이트 | 지도 | 무엇을 읽는가 |
|---|---|---|---|
| A | flawed | 있음 | 재현율 — 68건 중 몇 건 |
| B | flawed | 없음 | 지도가 재현율을 올렸는가 |
| C | clean | 있음 | 정밀도 — 오탐이 몇 건 |
| D | clean | 없음 | 지도가 오탐도 같이 올렸는가 |

> **판정 기준을 미리 못박는다.** 지도가 재현율만 올렸으면 채택. 재현율과 오탐이 같이
> 올랐으면 기각 — 그건 지도가 도운 게 아니라 에이전트를 수다스럽게 만든 것이다.
> C·D가 없으면 이 구분이 불가능하다.

### 먼저 인정하고 들어가는 상한

- 뷰포트가 1280×800 데스크톱 고정이라 **375px에서만 드러나는 3건은 원리적으로 못 잡는다.**
- 에이전트 단독으로는 68건 중 32건이 한계다. 나머지 32건은 계산된 시각 정보 없이는 못
  잡는다 — 그 격차가 차별점 ②의 근거다.
- flawed는 결제가 완주되지 않아 답사가 5/6에서 멈춘다. 완료 화면은 `unreached`에 사실로
  기록된다.

## 7. 비용 — 이미지는 답사 한 번에만 쓴다

첫 답사자만 스크린샷을 쓰고, 뒤따르는 100명은 그 설명서만 읽는다. 그래서 이미지 호출이
스텝 수에 100을 곱하지 않는다.

| | 값 |
|---|---|
| 답사 이미지 호출 | 40–60회 (스텝 수만큼, 1회성) |
| 페르소나 100명의 이미지 호출 | **0회** |
| 100명 탐색 텍스트 호출 | 최대 3,000회 (1회 실행) |
| 100명 기록 크기 | 약 31MB (실측 310KB / 30스텝) |

스텝마다 이미지를 넣는 방식이었다면 100명 × 30스텝 = 3,000회의 **비전** 호출이 된다.
설명서를 한 번만 만들어 돌려 쓰는 구조가 그 차이를 만든다.

실수로 100명이 도는 것을 막기 위해 실행기 기본값은 **한 명**이다. 100명은 명시적으로
요청해야 하고, 예상 호출 수를 보여준 뒤 한 번 더 묻는다. 금액 상한을 넘으면 그 자리에서
멈추고 종료 사유를 따로 남긴다.

> **발표에 쓸 때 주의.** "이미지 3,000회 → 40회"는 UXAgent 방식과 비교한 값이지 우리가
> 겪은 과거가 아니다. 그렇게 명시할 것. "60분 → 30분"은 아직 실측이 없으므로 4회 실행
> 뒤에 쓸 것. 단가표도 아직 콘솔 확인 전 추정치다.

## 8. 현재 상태 — 어디까지 됐고 무엇이 막혀 있나

| 구성요소 | 상태 | 확인된 것 |
|---|---|---|
| `snapshot.py` | 완료 | clean 기준선 0/0/0, 오탐 2건 수정 |
| `scout.py` | 완료 | 링크만으로 clean 6/6, 결제 완주 도달 |
| `generate.py` | 완료 | 고유 쌍 100/100, 최장 프롬프트 109자 |
| `run.py` | 완료 | 양쪽 실행·저장, 예산 상한, 맴돌이 판정 |
| `diary.py` | 완료 | 답사 일기·페르소나 기록 둘 다 읽음 |
| `viewer/index.html` | 미착수 | 와이어프레임 재생 |
| 채점·4회 실행 | 미착수 | 재현율·정밀도 |
| LLM 크레딧 | **막힘** | 전 모델 429 — 결제 연결 필요 |

> **가장 큰 미검증 항목.** 지금까지의 모든 실행은 모의 정책(`--mock`)으로 돌았다.
> 행동·화면 수치는 진짜지만 **사고 기록만 가짜**다. 파이프라인이 끝까지 도는 것은
> 확인됐고, 크레딧이 붙는 즉시 그 자리에 실제 판단이 들어간다.
> 100명을 돌리기 전에 3~5명으로 프롬프트를 먼저 손볼 것.

### 남은 순서

1. 뷰어 — 기록만으로 만들 수 있고 토큰이 들지 않는다.
2. 크레딧 연결 후 답사자 실제 실행 2회(clean/flawed) — 지금 지도는 자리표시자다.
3. 페르소나 3~5명으로 프롬프트 조정.
4. 4회 본실행 → 채점 → 발표 수치 확정.
